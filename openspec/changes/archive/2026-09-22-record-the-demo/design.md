## Context

See proposal.md for why. What matters here is what was proved before it was
written, because two of the four parts of a fake store were found by trying
rather than by reading.

`vhs 0.11.0` and `ffmpeg` are installed on this machine. Neither is added to the
flake's dev shell by this change: the target reports what is missing rather than
pinning a recording tool into every developer's shell.

## Goals / Non-Goals

Goals: a demo that shows the features the bean lists; fixtures that contain
nothing from anyone's disk; a recording anyone can reproduce byte for byte from
a clean checkout.

Non-Goals: recording at release time. Publishing to vhs.charm.sh. Any change to
the application. A tape that exercises a feature by editing files while it
records, which would make the recording depend on its own timing.

## Decisions

### Fixtures, not this repository

Three reasons, in the order they were found. The picker publishes whatever the
scan directories hold, and here that is twenty-seven real project names. A
recording made from a working tree is different every week. And the difference
view needs an active change, of which this repository has exactly one at a time
and sometimes none.

Its own content is genuinely good material, 27 specs and 599 scenarios of real
prose, and that is what makes the first reason worth stating: the fixtures are
not a fallback for having nothing to show, they are the only way to show it
twice.

### The startup state is pinned in every tape

A trial tape run from a directory that was not a project produced this, and then
swallowed every key sent after it:

```
  ┌────────────────────────────────────┐
  │   No OpenSpec project here.        │
  │   Open the project picker? (y/n)   │
  └────────────────────────────────────┘
```

So each tape opens with a hidden block that enters the fixture project and
exports the environment, and every `spg` in a tape passes `--config`. A tape
that relied on the working directory would record correctly on the machine it
was written on and nowhere else.

### The store is fake, and three of its four parts are files

Faking a store-backed project was the one unknown worth spending time on, since
the `store` column and the store mark are what the picker has that no other
listing does. It resolves with:

```
  <store>/.openspec-store/store.yaml       version, id, remote
  <repo>/openspec/config.yaml              store: tideclock
  registry.yaml                            backend.local_path → the store root
  XDG_DATA_HOME                            where the registry is read from
```

The first three were found by reading `ReadStoreMetadata` and `StoreInfoWith`.
The fourth was found by recording the picker and seeing `store: unresolved`
against the row, which is the report the application gives when the metadata
file is absent, and which is worth knowing works.

`local_path` is compared against the store's root through `samePath`, which
resolves symlinks on both sides but does not make a relative path absolute. So
the registry is generated by the target from `$(PWD)` and is not committed. It
is the only part that cannot be.

### One tape per feature, and a hero

At ten kilobytes a second a single recording is affordable, so the split is not
about size. It is about what a change to one pane costs: sixteen commits touched
`src/ui/` in the day before this was written, and six of them altered what is on
screen. A feature that moves should invalidate the fifteen seconds that show it.

The hero leads with the spec detail view rather than the change list. A reader
can already picture a table of changes from the README; an outline beside a card
is the part that has no equivalent elsewhere, and unlike a list it reads as
something while the GIF is still loading.

### The fixtures are a harbour

Short names, so nothing truncates in the change list's columns. Obviously
fictional, so nobody reads them as a real customer. Concrete enough that the
spec prose is about something, because a spec written about `example-app` doing
`the thing` demonstrates the format and not the tool:

```
  harbour-app    the project that is opened
  tideclock      the store its specs and changes live in
  ferry-times    a second project, so the picker has rows
  quay-signage   a third
```

### Nothing is recorded that writes to a real location

The export shot writes a zip. The demo config sets `export_dir` into
`demo/out/`, which the target creates and `.gitignore` covers, so recording the
demo twice leaves nothing behind and touches no home directory.

### The recordings are committed, and staged from a neutral path

Two things were found by recording and reading the frame rather than by
thinking about it.

The project header prints the project's absolute path, so recording in the
checkout published the recorder's home directory and directory layout in every
frame. The fixture is copied to a fixed neutral path and recorded from there,
which also means a clone lands wherever it lands and still records the same
content.

And the recordings have to be committed, because the README shows them: a GIF
that only exists after `make demo` is a broken image for everyone who did not
run it. That is 2.5 MB in the repository and another 2.5 MB in its history
every time they are re-recorded, which is the price of a README with pictures in
it and is worth naming rather than discovering.

## Risks / Trade-offs

- The recordings go stale silently, and nothing fails when they do. → The target
  stamps the version and commit it recorded at into `RECORDED_AT`, so a stale
  GIF can be identified as one. Recording at release time is the real answer and
  is deferred rather than pretended at.
- Re-recording rewrites 2.5 MB of binaries, and git keeps every version. → The
  alternative is a README with no pictures. Worth knowing before the tenth
  re-record rather than after it.
- A fixture spec has to be good enough to read on screen and is written by the
  same hand as the tool. → It is short. Four requirements across two specs is
  enough to fill an outline, and more would be a second thing to maintain.
- `vhs` is not in the flake. → The target says what is missing and how to get
  it. Pinning a recording tool into every shell to record a GIF nobody records
  daily is the wrong trade.
- The timings in a tape are guesses about how fast a reader reads. → They are in
  one place per tape and are the cheapest thing in this change to revise, which
  is an argument for recording early and adjusting rather than for getting them
  right first.

## Migration Plan

None. Nothing the application reads is touched.
